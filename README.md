The application begins by creating an interview session using a unique session ID along with the candidate’s information, including their member ID, name, job role, years of experience, educational background, current status, mission history, and performance indicators such as the number of completed missions, successful first attempts, and consecutive commitment days. For example, the initial request can be structured as `{ "sessionId": "abc-123", "candidate": { "member": { "id": "m_01", "name": "...", "jobRole": "...", "yearsExperience": 3, "education": "...", "status": "active" }, "missions": [{ "day": 9, "title": "Embeddings", "passed": true, "attempts": 1 }], "signals": { "commitDays": 21, "missionsCompleted": 24, "missionsFirstTry": 15 } }`. After the session has been initialized, each subsequent request uses the same session ID and contains the candidate’s latest response in the format `{ "sessionId": "abc-123", "message": "Candidate's answer goes here" }`. The system processes the response and generates the next interviewer turn while also maintaining the interview progress. Once the interview is completed, the system produces a structured feedback object containing the evaluation results. In addition, the `/api/tts` endpoint converts the interviewer’s responses into MP3 audio, allowing the interview to support voice-based interaction.

The project can be run locally by cloning the repository, installing the required dependencies using `npm i`, and starting the development server with `npm run dev`. The application is built using TanStack Start, TypeScript, React, and Tailwind CSS. The main interview functionality is implemented in `src/lib/interview-engine.server.ts`, which manages the interview state, retrieval process, and question-planning logic, while `src/lib/interview-types.ts` contains the shared types used by the API. The interview endpoint is implemented in `src/routes/api/interview.ts` with Zod-based validation, and `src/routes/api/tts.ts` handles voice output. The user interface includes a candidate selection component and an interview chat interface with audio playback, while the curriculum and candidate information are maintained in the `src/data` directory.

The application runs on `http://localhost:8080` during development. Model interactions are handled through the Lovable AI gateway using Gemini Flash for the interview loop, which means a separate model API key is not required for the current implementation. At present, session information is stored in memory, which is sufficient for demonstration purposes but would need to be replaced with a persistent database or storage solution for a production environment. The curriculum and candidate information are synthetic datasets provided as part of the project requirements, and authentication, user accounts, and access control were not included because they were outside the scope of the challenge.

Most of the core development work was focused on the interview engine, retrieval and question-planning logic, API contract, prompt design, and iterative tuning of the interview flow. Particular attention was given to ensuring that the interviewer does not terminate the session prematurely or repeatedly ask similar questions. Lovable was used to accelerate parts of the initial application development, including the basic project scaffolding, chat and candidate-selection interface, TTS integration, and supporting boilerplate. The main application logic and decisions related to the interview workflow, prompting strategy, and system behavior were developed and refined as part of the project implementation.
